## 1. Mission

Phase 3 turns `(InstanceView, RankedFile[])` into one or more **patch
candidates** — unified diffs that, when applied at `base_commit`,
should fix the bug described in `view.problem_statement`.

It is the **load-bearing** phase of the pipeline. Per
`docs/V10_TARGET_60PCT_PRO_SPEC.md` §2:

> Final pipeline score ≈ (file recall) × (patch generation success | correct files) × (selection accuracy)
>
> For 60% final score with Phase 1 at ~95% top-10:
>   `0.95 × patch_gen × selection = 0.60` → `patch_gen × selection = 0.63`
>
> Realistic ceiling on selection is ~0.90, so **patch_gen needs to land in the 66-74% band** when given the correct files.

Currently published patch-generation rates on Pro-difficulty
instances are 40-55%. Hitting 66-74% is the central engineering
problem of the project.

Per spec §3.3, on Pro the patch generator must:

  - Reason about multi-file changes (Pro median touches 1.8 files;
    many touch 3-5).
  - Use library APIs the model hasn't seen heavily during training.
  - Generate patches that pass the hidden FAIL_TO_PASS suite, not
    just the public tests.
  - Handle off-by-one, error handling, type coercion, None-handling,
    thread-safety edge cases.

Phase 3 V0 (this doc) targets **the dev/iteration scaffolding** for
that goal, not the final-quality generator. Per the model swap plan,
all dev iterates on **deepseek-chat**; the leaderboard run swaps in
Opus 4.7 via env-var override at the patch-gen role.

## 2. The contamination model for Phase 3

Phase 3 introduces patches and trajectories. Three new pieces of
state, with strict in/out rules:

| Artifact | Generated by | Read by | NEVER read by |
|---|---|---|---|
| `PatchCandidate` | Phase 3 (pipeline / agent) | Phase 4 validator + Phase 5 selector | itself (no candidate sees other candidates' diffs during gen) |
| `Phase3Trajectory` | Phase 3 (per-instance + per-route + per-candidate) | post-hoc audit | the next instance's generator (no cross-instance memory in V0) |
| `PatchGenContext` | Phase 3 (the assembled prompt context) | the LLM call only | persisted only to trajectory (audit), never re-fed to a model |

### 2.1 Hard rules (firewall-enforced)

  1. **No `harness.patch_gen` / `harness.agent` module imports
     `harness.repro`.** Per Phase 2 design §2 and the cross-phase
     firewall test (commit 17c), the patch generator must never see
     `ReproTestCase`. It may receive `ReproSignal` (a status
     summary), but only via `Phase4` after candidate generation —
     **not as input to generation**.
  2. **No `harness.eval` import outside `harness/eval.py`.** Eval
     verdicts are post-submission grader output; selection NEVER
     reads them.
  3. **Patch-generator-context-superset assertion (per Phase 2
     §3.1).** Whatever files the repro generator saw for instance
     `i`, the patch generator MUST also see for the same `i`. This
     guarantees any repro is structurally satisfiable.
     Implementation: at context-build time, before any LLM call,
     `assert set(repro_context_files_for(i)).issubset(set(patch_context_files_for(i)))`.
     Violation is a `ContextSupersetError`, caught cheaply.
  4. **Forbidden-token guard at generator output.** Patches and
     agent tool-call arguments are run through the same word-
     boundary forbidden-token detector used in Phase 2 (`harness.
     repro._detect_forbidden_tokens`). Hits log a WARNING and
     surface in the trajectory; in V0 they do NOT block. Real
     prevention is at the input layer (the prompt is built from
     firewall-clean fields).
  5. **Cross-instance memory is OFF in V0.** No
     `repo_cache/cross_instance_memory.json` may be read by the
     patch generator. Bet A (REPO_NOTES) is allowed (per-repo,
     pre-computed, no oracle data); cross-instance pattern learning
     (Bet #6 in V10_DESIGN.md §4.3) is deferred to a later phase.

### 2.2 New cross-phase firewall tests

Existing test (commit 17c, `tests/test_repro_firewall.py::test_no_phase3_module_imports_harness_repro`)
enumerates a flat list of candidate filenames at `harness/<name>.py`.
P3b extends this in two ways:

  - **Walk subdirs.** The Phase 3 layout uses `harness/patch_gen/`
    (a subdir, not a flat file). The test must `rglob` under
    `harness/` and treat any module whose path contains
    `patch_gen/`, `agent.py`, or `selection*.py` as a Phase 3
    candidate. The candidate-list constant becomes a glob list,
    not a basename list.
  - **Two new firewall tests** added to
    `tests/test_repro_firewall.py` (or a new
    `tests/test_phase3_firewall.py` if the file gets too long):
      - `test_no_phase3_module_imports_harness_repro` — same intent
        as 17c, widened to subdir scanning per above.
      - `test_no_phase3_module_imports_harness_eval` — new; mirrors
        the Phase 2 → Phase 3/5 firewall. `harness.eval` is the
        post-submission grader; selection NEVER reads its outputs.
      - `test_phase3_context_superset_assertion_present` — AST
        scan that confirms every prompt-build path in
        `harness.patch_gen` calls
        `harness.patch_gen.context._build_with_superset_check`
        before the LLM call. Refactors that bypass the assertion
        fail this test.
      - `test_phase3_no_cross_instance_memory_imports` — fail if
        `harness.patch_gen` imports anything from a
        `harness.memory.*` module (placeholder for Bet #6 future
        work, explicitly OFF in V0).

These four tests land in P3b alongside the Phase 3 implementation,
not as a separate commit. Their presence is a P3b acceptance gate.

## 3. Architecture

### 3.1 Two paths, three routes

Per `V10_DESIGN.md` §3.4 (the original brief), Phase 3 has two paths
and three routes between them:

| Route | Stages run | Cost (DeepSeek dev) | When it fires |
|---|---|---|---|
| `pipeline_only` | pipeline K=2 | ~$0.10/inst | est_difficulty ≤ EASY_THRESHOLD |
| `pipeline_then_agent` | pipeline K=2; if all candidates fail validation, agent K=1 (T_max=20 in dev) | ~$0.10 hit / ~$0.50 miss | EASY < est_difficulty < HARD |
| `agent_first` | agent K=1 (T_max=20 in dev) | ~$0.40/inst | est_difficulty ≥ HARD_THRESHOLD |

**V0 simplification (per the spec's "start with the cheapest config"):**
Phase 3 V0 lands `pipeline_only` for ALL instances first. The agent
path lands separately in commit P3c. Routing thresholds are stubbed
to `est_difficulty <= +inf` (everyone takes pipeline) until the
agent path exists. Once both exist, routing is calibrated on dev_50.

### 3.2 Pipeline path (P3b)

**Single-shot prompt** to DeepSeek:

  - System: instructions on producing a unified diff, the constraint
    that the patch must apply at base_commit, the schema for the
    expected JSON output.
  - User: structured table — issue text, file map (top-K=10 files
    with their contents up to per-file char cap), test directory
    layout.

**K candidates** generated by varying temperature: K=2 for dev
(temperatures 0.0 and 0.5); K=4 for the leaderboard (0.0, 0.3, 0.7,
1.0). Each is one independent LLM call; no candidate sees any other.

**Output schema (frozen):**

```python
@dataclass(frozen=True)
class PatchCandidate:
    instance_id: str
    candidate_id: str            # "pipe_t0" / "pipe_t05" / "agent_a0_final"
    diff: str                    # unified diff, repo-relative paths
    source_route: str            # "pipeline" | "agent"
    source_temperature: float | None  # None for agent
    source_attempt_index: int    # 0..K-1
    generator_model: str
    generator_input_tokens: int
    generator_output_tokens: int
    generation_cost_usd: float
    duration_s: float
```

`__post_init__` validates: `diff` is non-empty, `candidate_id` is
non-empty, no field name matches a forbidden token. The `diff` field
is *not* scanned for forbidden tokens at construction (patch
contents may legitimately include code fragments containing words
that look like forbidden substrings under naive matching); the
output guard (§2.1 rule 4) runs at the boundary.

**Per-instance pipeline cost cap:** `$1.00` in dev, `$5.00` in
production. Enforced via `harness.cost.CostTracker` instantiated per
instance. Exceeding the cap mid-K returns the candidates produced so
far + a budget marker; not an error.

**Context budget management.** Phase 1 audit found 11/16 cap-hitter
instances exceed 800K tokens even with compression
(`docs/audits/v10_projected_context_for_cap_hitters.md`). For those
instances:

  - Pipeline path detects the projected size >700K and falls back
    to a **per-file streaming** mode: top-K files are sent in order,
    one file per LLM call, asking the model to identify which files
    need editing. Then a final call assembles the diff. Costs about
    2× a normal pipeline call but stays under the context limit.
  - The agent path is the natural shape for these instances; the
    per-file streaming pipeline is a fallback for cases where we
    want a pipeline candidate alongside the agent's.
  - V0 P3b just emits a `ContextOversizeError` instead of running
    the pipeline call for these instances. The streaming fallback
    is P3b-followup; the agent path covers them in P3c.

### 3.3 Agent path (P3c)

A multi-turn ACI (Action-Chunked Iteration) loop. The agent has a
small, audited tool surface:

| Tool | Purpose | Forbidden-token guard |
|---|---|---|
| `read_file(path, offset_line, limit_lines)` | scoped file read | path scanned at boundary |
| `search_text(query, glob)` | ripgrep across the worktree | query + glob scanned at boundary |
| `list_dir(path)` | directory listing | path scanned at boundary |
| `apply_patch(diff)` | try the patch, return apply-success only (not validation result) | diff scanned at boundary |
| `submit(diff)` | finalize the candidate | diff scanned at boundary |

**Tools we deliberately do NOT expose:**

  - `run_tests(...)` — leak surface. The agent never names a test
    selector. Validation happens in Phase 4 with a fixed test list
    from `view.test_directives`.
  - `read_metadata(...)` — no oracle field reads.
  - `run_repro(...)` — Phase 2 repro test contents are hidden from
    the agent. The agent doesn't even know whether a repro exists.

**Turn budget (dev):** `T_max = 20`. Lets the agent explore, locate,
patch, and self-revise twice. Hard ceiling at 20 turns regardless of
whether it has produced a candidate. Per spec §11 (cost-aware
routing): T_max for the leaderboard run is 30/50 by difficulty.

**Per-instance cost cap:** $0.50 in dev (DeepSeek), $5.00 in
production. Cost tracker sees every LLM call; if cumulative spend
crosses 80% of cap, the agent gets a final-turn forced-finalize
prompt: "you have one turn to submit your best diff."

**Single-candidate in dev, K=2 in production.** Two prompt framings
(cautious / exploratory) for K=2 in production; single framing for
K=1 in dev.

**Action-chunked: each LLM turn must produce one tool call.** No
free-form prose; the tool schema is enforced via JSON Schema in the
DeepSeek `response_format`. If the model emits invalid JSON or no
tool call, we re-prompt with the parse error and decrement T_max by
1.

### 3.4 Difficulty estimation (P3-routing, lands in P3d)

Cheap signals computed once per instance, before any expensive work:

  - `issue_token_count` — `view.problem_statement` length.
  - `traceback_present` — Stage 1c output.
  - `candidate_file_count` — Phase 1 top-K count.
  - `multi_file_scope_words` — count of "files", "modules",
    "across the codebase" in problem_statement.
  - `repo_difficulty_prior` — `splits/v7_difficulty_priors.json`
    when available; default 0.5.
  - `repo_skew` — django/sympy → +0.1; flask/requests → −0.1.

Combined into a 0..1 score by a hand-tuned linear formula initially
(weights from spec § references); replaced by a small learned
classifier if dev_50 routing accuracy is below 70%.

**Defaults:** EASY_THRESHOLD = 0.30, HARD_THRESHOLD = 0.70. Both
are calibrated on dev_50 in P3d.

### 3.5 Module layout

```
harness/patch_gen/
  __init__.py              — public API: generate_pipeline, generate_agent
  pipeline.py              — single-shot K-candidate generator
  agent.py                 — multi-turn ACI loop (lands in P3c)
  context.py               — context assembly (file reads, AST snippets,
                             oversize handling); _build_with_superset_check
                             is the only public entrypoint per §2.2
  routing.py               — est_difficulty + route() (lands in P3d)
  views.py                 — PatchCandidate + supporting frozen dataclasses

harness/sandbox.py         — extends with apply_patch() (already exists),
                             reset_worktree() (already exists). No new
                             test-runner methods.

harness/llm/clients.py     — already routes role->model; no change.

harness/config/models.yaml — already has patch_generator_pipeline,
                             patch_generator_agent roles set to deepseek-chat.

tests/test_patch_gen_pipeline.py
tests/test_patch_gen_agent.py
tests/test_patch_gen_context.py
tests/test_no_oracle_leak.py — extended with the four new firewall tests.
```

The `harness.patch_gen.context` module owns the context-superset
assertion. ALL prompt builders import context-build only via that
module's `_build_with_superset_check`. This makes the assertion a
single chokepoint that the firewall AST scan (§2.2) can verify.

## 4. Data flow

```
InstanceView (frozen, oracle-free)
        |
        v
[Phase 1 retrieval+rerank] —→ RankedFile[] (top-K=10)
        |
        +---→ [Phase 2 repro-gen] —→ ReproSignal (status only; not test code)
        |                                   |
        v                                   |
+----- harness.patch_gen.generate(view, ranked_files) ----------+
| 1. _build_with_superset_check(view, ranked_files):           |
|    - read top-K file contents (cached per instance)          |
|    - assert set(repro_context_files) ⊆ set(patch_context_files)
|    - return PatchGenContext                                  |
| 2. routing.route(view, ranked_files, signals)                |
|    → "pipeline_only" / "pipeline_then_agent" / "agent_first" |
| 3a. pipeline_path(context, K):                               |
|     for t in temperatures[:K]:                               |
|       call DeepSeek with PatchGenContext at temperature=t    |
|       parse → PatchCandidate                                 |
|     return list[PatchCandidate]                              |
| 3b. agent_path(context, T_max):                              |
|     loop up to T_max turns:                                  |
|       observe → think → tool_call                            |
|       if tool_call is submit: finalize PatchCandidate, break |
|     return [PatchCandidate]                                  |
+---------------------------------------------------------------+
        |
        v (separate channel; selector reads CandidateView in Phase 5)
PatchCandidate[] handed to Phase 4 validator
```

Notes on what flows where:

  - **InstanceView, RankedFile[]**: visible to both paths.
  - **ReproSignal**: NOT visible to the patch generator. It's
    composed into the eventual CandidateView for Phase 5.
  - **PatchCandidate.diff**: written to disk + handed to Phase 4.
  - **Per-turn agent state**: persisted to
    `runs/<run-name>/patch_gen/<iid>/agent_<aid>/turn_NNN.jsonl`
    for audit. Same shape as Phase 1's trajectory log.

## 5. Cost model (DeepSeek dev)

Per-instance cost (estimates, refined by P3b smoke):

| Stage | Tokens (input/output) | $ |
|---|---|---|
| Pipeline K=2 attempt 0 (T=0) | 25K / 1.5K | $0.020 |
| Pipeline K=2 attempt 1 (T=0.5) | 25K / 1.5K | $0.020 |
| Per-instance pipeline subtotal | | **$0.04** |
| Agent T_max=20 (avg ~10 turns when fired) | 8K × 10 / 1K × 10 | $0.30 |
| Per-instance agent subtotal (when fired) | | **$0.30** |
| Bet A (REPO_NOTES, amortized over ~5 inst/repo on dev_50) | | $0.05 |
| **Per-instance worst case (pipeline + agent both fire)** | | **~$0.40** |

**Dev_50 budgets:**

  - **P3b dev_50 (pipeline only):** 50 × $0.04 = **$2** + Bet A $2.50 ≈ $4.50.
  - **P3c dev_50 (agent path solo, single candidate):** 50 × $0.30 = **$15**.
  - **P3d dev_50 (full routing, pipeline + agent overlap):** 50 × $0.20 weighted = **$10**.
  - **P3e dev_100 patch-gen eval (full routing):** 100 × $0.20 = **$20**.

Total Phase 3 dev spend bounded at **~$50**, well under the spec's
$30/iteration cap × 8 iterations = $240 ceiling.

## 6. Acceptance criteria for Phase 3 → Phase 4 advance

Per spec §3.3 (the central engineering target) and the long-horizon
batch's per-phase gate:

  1. **dev_50 pipeline-only patch correctness:** ≥40% of patches,
     when given correct files, apply cleanly AND pass the gold's
     hidden FAIL_TO_PASS at eval. (The eval-only path under
     `harness/eval.py` is the only place this is measured; result
     is reported in the audit but never feeds back into
     generation.) Below 40%, the pipeline is not load-bearing on
     its own; bring up the agent path before iterating further.
  2. **dev_50 full-routing patch correctness:** ≥50% per the
     long-horizon batch threshold. Below 50% after 8 iterations is
     a hard-stop redesign trigger.
  3. **dev_100 generalization:** the dev_50 number must hold on
     dev_100 within ±5pp. Fold drift greater than 5pp triggers a
     rerun of the dev_50 calibration before continuing.
  4. **Cost on dev_50 full-routing run:** ≤$25 actual spend (vs
     $10 estimate; 2.5× headroom for unexpected agent-path
     escalation).
  5. **Firewall green:** all four new firewall tests pass; no Phase
     3 module imports `harness.repro` or `harness.eval`; the
     context-superset assertion is the only context entrypoint.
  6. **Cross-instance memory firewall:** no Phase 3 module imports
     `harness.memory` (placeholder for Bet #6 future work).

If (1) drops below 30%, the design needs rethinking — likely the
pipeline prompt or the per-file context assembly is wrong, not the
model. Drop to per-file streaming and re-test before iterating
further.

## 7. Open design questions — resolved candidates

The following positions are baked in but flagged as the most likely
revision targets in review.

### 7.1 K=2 vs K=4 in dev — RESOLVED

K=2 (temperatures 0.0, 0.5). Rationale: dev iteration cycles need
to be cheap and fast; K=4 doubles cost without doubling information
in the early-iteration regime. K=4 returns for the leaderboard run
under the env-var override.

### 7.2 Pipeline path's prompt format (raw diff vs JSON-wrapped diff)

Resolved: **JSON-wrapped diff with rationale.** `{"rationale": "...",
"diff": "..."}`. Costs ~50 extra output tokens per candidate but
gives the trajectory audit a "why" for every candidate, which is
useful both for paper material and for the §6 calibration story.

### 7.3 Agent tool surface — RESOLVED

Five tools (`read_file`, `search_text`, `list_dir`, `apply_patch`,
`submit`). No `run_tests`. Apply-patch returns apply-success only;
the agent never sees public-suite or repro results. The agent is
effectively blind to validation, by design — validation is Phase 4's
job, not the agent's.

### 7.4 Context-oversize handling on cap-hitter instances — RESOLVED

P3b: emit `ContextOversizeError` for instances > 700K projected
tokens. P3c: agent path covers them naturally (per-file streaming
is the agent's natural shape). The pipeline streaming-fallback is
deferred to P3b-followup; not in V0 scope.

### 7.5 Per-turn cost guard for the agent — RESOLVED

Cumulative spend > 80% cap → forced-finalize on next turn.
`degraded=true` in the trajectory. Same shape as the V10_DESIGN.md
§3.4 spec for the turn budget.

### 7.6 (NEW) When does Phase 3 see a partial repro?

If Phase 2 returned `ReproStatus.NO_REPRO` or
`ReproStatus.NO_REPRO_BUDGET` for instance `i`, Phase 3 still runs.
Phase 4 records `repro_signal=None`; Phase 5 weighs the signal
accordingly. The patch generator is unaware of the repro's
existence either way (per §2.1 rule 1), so this is invisible to
Phase 3.

### 7.7 (NEW) Ablation entries for the dev_50 patch-gen sweep

The dev_50 run produces an ablation row in `paper/ablations.md`
mirroring the existing Phase 1 ablation table:

  - `pipeline-only` (K=2)
  - `pipeline-only` (K=4) — to size the K=2 → K=4 lift
  - `agent-only` (K=1, T_max=20)
  - `pipeline-then-agent` (default routing)
  - `pipeline-only` with REPO_NOTES on/off (Bet A)
  - `pipeline-only` at temperature 0 vs 0.5 (the K=2 pair)

Each row: `n_correct / n_total`, cost, mean wall-clock. The
ablation table doubles as the §6 evidence package.

## 8. What's NOT in this design (deferred)

  - **Per-instance Opus escalation (cost-aware routing).** Spec §11
    suggests routing easy → DeepSeek, hard → Opus. V0 stays on
    DeepSeek throughout; the leaderboard run env-var swaps roles.
    Per-instance routing among models is P3-followup.
  - **Multi-file plan-then-implement (spec §4.1).** V0's pipeline
    is single-shot for single-file fixes; multi-file fixes hit the
    agent path. The plan-then-implement pattern is P3-followup if
    the agent path's multi-file rate is below 50%.
  - **Adversarial test generation (Bet B from V10_DESIGN.md §4.2).**
    Bet B is a Phase 4 component (validation) — adversarial tests
    are run against candidates after generation. Out of scope for
    Phase 3.
  - **Cross-instance memory (Bet #6 from V10_DESIGN.md §4.3).**
    Explicitly forbidden in V0 (§2.1 rule 5). Re-evaluate after
    end-to-end dev_100 lands.
  - **Devil's advocate critique loop.** Spec §3.7 deferred this to
    Phase 6 (refinement) — out of scope for Phase 3.

    Phase 3 code lands.

    dev_50 calibration before continuing.

## 11. Acceptance gate for THIS DESIGN DOC

Per the long-horizon batch spec (commit P3a):

> Stop after this lands. Wait for human ack before any Phase 3 code.

Open questions surfaced for explicit ack:

  1. **§3.1 V0 simplification.** Does P3b land pipeline_only with
     all instances routed there, or does P3b land routing AND
     pipeline simultaneously, with agent stub returning empty?
     Recommendation: **simpler** — P3b is pipeline+routing-stub;
     P3c is agent path; P3d wires routing + both paths.
  2. **§3.2 Per-file streaming pipeline.** Is the streaming
     fallback in scope for V0, or do cap-hitter instances just
     emit `ContextOversizeError` and skip pipeline entirely
     (relying on the agent path in P3c)? Recommendation: **skip
     pipeline; agent covers them.**
  3. **§3.3 Agent tool surface.** Five tools as listed, or do we
     also need `run_shell` for arbitrary commands? Recommendation:
     **no `run_shell`** — the firewall is harder to enforce and
     the five-tool surface covers all observed agent patterns.
  4. **§3.4 Difficulty heuristic — linear or learned.** Linear
     formula for V0; learned classifier if dev_50 routing accuracy
     < 70%. Recommendation: **linear V0, escalate if numbers
     don't move**.
  5. **§6 Acceptance bar (40% pipeline-only, 50% full-routing).**
     The spec target is 66-74% which the doc takes as the
     ultimate target; the V0 acceptance bar (40-50%) is a floor
     to confirm the architecture is sound, not the headline
     number. Recommendation: **bar stays at 40/50 for V0
     acceptance, headline is dev_100 full pipeline E2E**.

If any of (1)-(5) gets a "no" or "different recommendation," the
revision lands as P3a-followup before P3b. Otherwise P3b is
greenlit on ack.
