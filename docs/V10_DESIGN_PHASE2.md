# V10 Phase 2 Design — Reproduction Oracle

**Status:** draft, awaiting review.
**Author:** harness team.
**Phase 1 status (context):** stages 1a/1b/1c/1g landed; dev_50 result is 74% top-1 / 94% top-5 / 98% top-10 with rerank. Stages 1d/1e/1f deferred (decision doc at `docs/audits/phase1_stages_1d_1e_1f_decision.md`). dev_100 validation running concurrently with this design.
**Scope:** Phase 2 only. No code in this doc. Phase 3 (patch generation), Phase 4 (validation), Phase 5 (selection) are referenced but not designed.

---

## 1. Mission

Phase 2 builds the **reproduction oracle**: an LLM-generated pytest test, per instance, that should fail at `base_commit` and pass after a correct fix. It is a **selection signal**, not a target. Phase 3's patch generator never sees it.

Per V10_DESIGN.md §3.3 (the original brief that survives this Phase 2 design):

> Repro tests are NEVER shown to the patch-generation agent as "the test you must pass." They're used only as a SIGNAL during selection. This avoids over-fitting to our own oracle.

Phase 2 makes that rule structural — enforced by the firewall, not by convention.

---

## 2. The contamination model for Phase 2

Phase 2 introduces three new pieces of state:

| Artifact | Generated by | Read by | NEVER read by |
|---|---|---|---|
| `ReproTestCase` | sub-agent (LLM call) reading `InstanceView` only | Phase 4 validator | Phase 3 patch generator |
| `ReproSignal` | sandbox runner | Phase 5 selector | Phase 3 patch generator |
| `repro_status` | sandbox-side verification | Phase 5 selector | Phase 3 patch generator |

**Hard rule:** the patch generator may only see `InstanceView` (no oracle fields). The repro test exists in a *separate channel* that flows from generator → sandbox → validator → selector. Phase 3's prompt builder must not import from `harness.repro` (the Phase 2 module). The firewall test enforces this with a new AST-scan rule:

```python
# tests/test_no_oracle_leak.py — new test
def test_no_phase3_module_imports_phase2_repro() -> None:
    """harness.repro produces ReproTestCase / ReproSignal which carry
    derived-from-issue-only test code. They are SELECTION signals, not
    generation prompts. No harness.patch_gen / harness.agent / harness
    rerank module may import from harness.repro."""
```

The reasoning is the same as the V8 leak: V8 used the eval verdict in selection. V10 must not use the repro test in generation. Both are "the answer feeding back into the question." The firewall is the only durable defense.

## 3. Repro generator architecture

### 3.1 Inputs (firewall enforced)

- `InstanceView` — the same frozen dataclass Phase 1 uses. No `gold_patch`, no `test_patch`, no `FAIL_TO_PASS`. The repro generator's prompt is built from `view.problem_statement` + `view.repo_skeleton` + `view.test_directives` only.
- Optionally: the Phase 1 reranked top-K files (from `RerankerOutput.ranked_files`). This is allowed because those files are derived from the issue text, not the gold. The generator may peek at the top-K to ground its repro in the right module.

### 3.2 Output: `ReproTestCase` (frozen typed dataclass)

```python
@dataclass(frozen=True)
class ReproTestCase:
    instance_id: str
    test_filename: str           # e.g. "test_repro_v10.py" — written into /testbed/<test_dirs>/
    test_code: str               # the pytest source
    target_test_id: str          # e.g. "test_repro_v10::test_user_creation_form_strips_whitespace"
    rationale: str               # one-paragraph why-this-test from the generator
    generator_model: str         # e.g. "deepseek-chat"
    generator_input_tokens: int
    generator_output_tokens: int
    attempt_index: int           # 0..N (multiple attempts may be needed)
```

The dataclass is field-name-validated against `FORBIDDEN_TOKENS` like every other view. `test_code` is a string but the contamination model is about who *reads* it; field-name validation isn't the concern here.

### 3.3 Sub-agent prompt design

System prompt (sketched):

```
You are writing a pytest test that reproduces a bug described in a
software-engineering issue. The test should:

  - FAIL at the current state of the repo (because the bug exists).
  - PASS after a correct fix is applied.
  - Be SELF-CONTAINED: import only what's needed; don't depend on
    fixtures defined elsewhere unless you also stub them.
  - Target the smallest reproducible scenario, not a comprehensive
    test of the affected feature.

You will be given:
  - the issue text,
  - a list of likely-relevant files (from the localizer),
  - the repo's test directory layout (so you place the test correctly),
  - one-line summaries of the candidate files (classes, functions).

Output only a JSON object:
  {
    "test_filename": "tests/test_repro_v10_<issue-slug>.py",
    "test_code": "...",
    "target_test_id": "tests/test_repro_v10_xxx::test_<descriptive_name>",
    "rationale": "<1-2 paragraphs>"
  }
```

User prompt: structured table — issue, top-K candidate files (path + summary + n_lines), repo's test directories.

Token budget: 30K input cap (issue + top-K summaries are small relative to Phase 1 reranker prompts). 4K output for the test code.

### 3.4 Verification step (must-fail-at-base)

Per the brief:
> Repro is run inside the sandbox at base_commit. We REQUIRE it to fail there before we trust it as a signal.

Concrete flow:

1. Generator emits `ReproTestCase` (attempt 0).
2. Sandbox starts at `base_commit`. Test code is `write_file`'d to `<test_dirs>[0]/<test_filename>` (default the first declared test dir).
3. Run the specific test via `Sandbox.run_repro_test(target_test_id)` — a NEW sandbox method that runs ONE test by selector. **This method validates the selector against forbidden tokens** (case-insensitive substring match per V10_DESIGN.md §12.5) so a generator-emitted selector containing a leak token would be refused at the sandbox boundary.
4. Capture exit code + stdout. Three terminal states:
   - **fails-at-base** ✓ — the test failed (i.e., the bug is reproduced). Trust it as a signal.
   - **passes-at-base** ✗ — the test doesn't exercise the bug. Discard.
   - **errors** ✗ — import error, syntax error, missing fixture. Discard.
5. If discard: re-prompt the generator with the test output as context, ask for an improved attempt. Up to **N=3** attempts total (attempt 0, 1, 2).
6. After 3 fails: emit `ReproStatus.NO_REPRO`. The instance proceeds without a repro signal.

`Sandbox.run_repro_test` is the new sandbox method:

```python
class Sandbox:
    def run_repro_test(
        self,
        *,
        test_path: str,          # relative to /testbed
        test_id: str,            # pytest selector like "...::test_xxx"
        timeout_s: int = 60,
    ) -> ExecResult:
        """Run ONE pytest test inside the container. Validates test_id
        against FORBIDDEN_TOKENS so a generator-emitted selector with
        a leak token (e.g., 'fail_to_pass_repro') is refused at the
        sandbox boundary, not at submission time."""
```

### 3.5 ReproSignal (the artifact selectors see)

```python
@dataclass(frozen=True)
class ReproSignal:
    status: str                  # 'pass' | 'fail' | 'no_repro' | 'errored'
    duration_s: float
    log_excerpt: str             # tail of pytest output (truncated)
    test_filename: str | None    # for traceability; selector doesn't need to read the test
    target_test_id: str | None
    attempt_index: int           # which attempt produced this signal (0..N-1)
```

This already exists in `harness/views.py` from Phase 0. Phase 2 wires the producer; the consumer (Phase 5 selector) is unchanged.

### 3.6 Property tests (scoped per the pushback in V10_DESIGN.md §3.3)

The original brief's Hypothesis property tests get **demoted to tie-break-only** based on the existing pushback. Phase 2 produces at most **2** Hypothesis properties per instance, alongside the main repro. They are recorded in `ReproSignal.property_results` as a separate field, and selectors only consult them when other signals tie.

Concretely:

- Generator is asked to emit 2 invariants the patched function should satisfy (e.g., for a sorting bug: `sorted(xs) is monotonically non-decreasing`).
- Hypothesis runs each invariant with default settings (max_examples=50). Pass/fail recorded.
- These signals don't need to fail at base — they're invariants, not bug repros. They DO need to pass after a correct fix.

If the generator produces no useful properties (rationale: "the bug doesn't lend itself to a property"), record `property_count=0` and skip. Don't force properties on bugs that don't have them.

### 3.7 Negative test (optional, scoped)

Per the brief:
> a test that explicitly passes at base_commit and should still pass after the fix. Catches over-broad patches that delete functionality.

Phase 2 v0 makes this **opt-out**: the generator is asked to emit ONE negative test alongside the repro. Cost is small (one extra LLM call's output token usage). If the generator can't think of a useful negative, it returns the empty string and we skip.

Recorded as `ReproSignal.negative_test_passed_at_base: bool | None` (None = no negative test generated).

## 4. Module layout

```
harness/repro.py            — generator + verification orchestration
                              (this is the new module)
harness/sandbox.py          — adds run_repro_test(test_path, test_id)
harness/views.py            — already has ReproSignal; nothing to add
harness/llm/clients.py      — already supports the deepseek-chat model
                              for role 'repro_gen' (V10 model config)
tests/test_repro.py         — unit tests for prompt build, parse,
                              must-fail-at-base flow (mocked LLM + sandbox)
tests/test_no_oracle_leak.py
                            — new firewall test:
                              no patch-gen/agent/rerank module imports
                              from harness.repro
```

The firewall test is the load-bearing addition. It encodes the contamination rule structurally so a future contributor can't accidentally pass `ReproTestCase` to the patch generator.

## 5. Data flow

```
InstanceView (frozen, oracle-free)
        |
        v
[Phase 1 retrieval+rerank] —→ RankedFile[] (top-K candidates)
        |
        v
+----- harness.repro.generate(view, ranked_files) -----------------+
| 1. Build prompt from view.problem_statement +                    |
|    ranked_files[0..K-1].file_summary                             |
| 2. LLM call (role='repro_gen', default deepseek-chat)            |
| 3. Parse JSON → ReproTestCase                                    |
| 4. sandbox.run_repro_test(...)                                   |
|    ├─ fails-at-base ✓ → return ReproTestCase + ReproSignal       |
|    └─ passes/errors → re-prompt with output, attempt +=1 (≤2)    |
+-------------------------------------------------------------------+
        |
        v (separate channel — patch generator never sees ReproTestCase)
ReproSignal stored on CandidateView for Phase 5 selection
```

The patch generator (Phase 3) reads `InstanceView` + `RankedFile[]` only. It never imports from `harness.repro`, never sees `ReproTestCase`, never knows the repro test exists.

The selector (Phase 5) reads `CandidateView.repro_signal` to weigh candidates. It still doesn't see the test code itself — only pass/fail/no_repro status + log excerpt.

## 6. Cost model

Per-instance Phase 2 cost (estimated for deepseek-chat, before measurement):

| Component | Tokens (input/output) | $ |
|---|---|---|
| Generator attempt 0 | 8K / 2K | $0.005 |
| Verification (sandbox exec) | — | ~free, ~30s wall |
| Re-prompt (if attempt 0 fails) | 12K / 2K | $0.007 |
| Re-prompt 2 (if 1 fails) | 16K / 2K | $0.009 |
| Property test gen | 4K / 1K | $0.002 |
| Negative test gen | 4K / 1K | $0.002 |
| **Per-instance worst case** | | **~$0.025** |
| **Per-instance typical (1 attempt + properties)** | | **~$0.009** |

Expected dev-50 cost: 50 × ~$0.015 (assume 30% need a retry) ≈ **$0.75**.
Expected test-500 cost: 500 × ~$0.015 ≈ **$7.50**.

Both well within the $50 batch cap.

The bigger cost is **wall-clock per instance**: each attempt does a full sandbox exec (~30 s for a small test, longer for django-class boot). Three attempts = ~90 s/instance for the worst case. dev_50 in serial: ~75 min. dev_100: ~150 min. Acceptable.

## 7. Acceptance criteria for Phase 2 → Phase 3 advance

Per V10_DESIGN.md split discipline, Phase 2 isn't done until:

1. **dev_50 repro coverage:** ≥60% of instances produce a `fails-at-base` repro within 3 attempts. Below 60%, the signal is too sparse to weight in selection.
2. **Property test rate:** ≥30% of instances produce ≥1 valid property. Below 30%, drop properties from the V0 design.
3. **Sandbox `run_repro_test` validates selectors:** the existing case-insensitive forbidden-token guard catches at least one synthetic leak attempt in tests.
4. **Firewall test passes:** no Phase 3 module imports `harness.repro`.
5. **dev-100 repro coverage:** ≥55% (some degradation expected on held-out).
6. **Cost on dev-50:** ≤$2 actual spend (vs $0.75 estimate; 2.5× headroom for unexpected retry rates).

If (1) drops below 50% even after prompt iteration, the design needs rethinking. If (2) drops below 20%, properties are dropped from V0 entirely.

## 8. Open design questions for review

These are the four points I want explicit ack on before any code lands.

### 8.1 Should `harness.repro` see the Phase 1 reranked file list?

**Pro:** the generator grounds its repro in the right module. The localizer's top-K is already derived from the issue text, so it's not a leak.

**Con:** if Phase 1's localizer is wrong, the repro generator inherits the wrong context. We may want the repro generator to look at the WHOLE skeleton, not just top-K.

**Recommendation:** pass `RankedFile[]` *and* `RepoSkeleton`. Generator decides what to use.

### 8.2 What's the verification window?

The brief says:
> Up to N=3 attempts; if it never fails, mark "no repro" and proceed without it.

**Question:** are 3 attempts the right N? More attempts = more cost + possible overfitting; fewer = lower coverage. The pushback in V10_DESIGN.md §3.3 said the generator's failures are a real signal, not just "try again."

**Recommendation:** start with N=3, instrument the actual fail-rate distribution, tune. If most useful repros come from attempts 0-1 and attempt 2 is mostly noise, drop to N=2.

### 8.3 Are property tests worth the complexity?

The pushback already demoted them to tie-break only. **Question:** at tie-break-only, is the engineering overhead worth it? Selectors at tie-break would consult them <10% of the time.

**Recommendation:** skip properties in V0. Add later if the dev_50 selection layer (Phase 5) shows that ties are common AND properties differentiate them. Otherwise it's premature complexity.

### 8.4 What does `Sandbox.run_repro_test` block?

The case-insensitive forbidden-token guard blocks selectors that mention `fail_to_pass`, `pass_to_pass`, `test_patch`, etc. **But:** what if the generator emits a test name like `test_validates_pass_to_pass_resolution`? That's a meaningful test name with `pass_to_pass` substring, but it's NOT pulling from oracle data — it's coincidental.

**Recommendation:** the guard fires on substring match (over-flag), and we accept the false positive rate. Generator gets re-prompted on the rare collision; pragmatic. Document the over-flag behavior in the firewall section.

## 9. What's NOT in this design (deferred)

- **Repro caching across reruns.** A repro test for the same `instance_id` doesn't change between V10 commits. We could cache it. Defer until cost becomes a concern.
- **Per-repo repro templates.** Some repos have boilerplate test setup that the generator re-derives every time. Could be a per-repo `REPO_NOTES.md` (Bet A from V10_DESIGN.md §4.1). Wire into Phase 2 only if generation cost grows.
- **Repro test coverage analysis.** "What fraction of the gold-patch's lines does our repro exercise?" Useful for a paper section; not needed for Phase 2 V0.
